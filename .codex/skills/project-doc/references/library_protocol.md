# 文档维护协议

适用于 arc-kit 的日常文档同步、内容重整和一致性审计。模块与测试入口见 [仓库导航](repository_map.md)；本协议规定知识放在哪里、何时更新以及如何验证。

## 文档分工与语言

| 载体 | 维护范围 | 同步条件 |
| --- | --- | --- |
| `README.md`、`README.zh-CN.md` | 产品能力、用户流程、CLI 参数、JSON、退出码、交互、开发与发布说明 | 对应行为或流程改变时同步两份，不要求逐字翻译，但契约、示例和限制必须一致 |
| `CONTRIBUTING.md`、`CONTRIBUTING.zh-CN.md` | 简短贡献入口 | 贡献规则、验证入口或链接改变时同步 |
| `built-in/` 中实际存在的资源说明 | 内置资源随产品分发的用法与约定 | 对应资源的内容或行为改变时评估同步；先确认文件存在 |
| `docs/` | 建立后的跨模块工程知识 | 系统边界、领域不变量、持久化格式、恢复流程或设计决策改变时同步 |
| `.codex/skills/project-doc/` | 文档协作规则和查证导航 | 工作流、文档布局、模块路由或技能约定改变时同步 |

现有 README 和贡献文件保持名称、位置及双语关系，不为了文档库命名规则移动它们。`docs/` 与本技能默认用中文；代码注释语言服从 `AGENTS.md`。命令、配置键、JSON 字段及符号名保持原样。示例使用虚构路径与占位凭据，不复制本机 provider 配置或登录态。

首次建立 `docs/` 时，同步 README 的双语“文档要求”章节，明确用户说明与工程文档的分工并添加真实存在的入口链接；不能保留“全部正式文档只在 README”这类排他性声明。尚未建库时只描述预定入口，不生成失效链接。

## 读取与证据

`docs/index.md` 存在时，每个任务先完整读取，再按“读取时机”进入相关分类和章节。根目录缺失时，按技能入口检查备忘录或使用仓库导航及现有 README；不能把不存在的目录写成已经核实的依据。

围绕任务收集足够的证据：入口及参数定义、核心实现、调用方、错误分支、测试和已有公共说明。当前工作区包括未提交和新增实现；历史记录只用于理解意图，不用它覆盖当前文件。

区分“代码现在怎样运行”和“用户要求改成怎样”。文档与实现冲突时，先核实是否为实现缺陷、说明过期或尚未完成的变更，再在任务范围内处理。只读审查报告冲突；文档重写不会自动授权修改程序行为。未能确定的高影响契约先标明缺口，不填入猜测。

## 决定写入位置

先更新拥有该事实的现有章节，再判断是否需要新文档。

- 用户可观察的参数、输出、错误、安装路径或流程变化，更新 README 的对应双语章节；已建库时评估关联工程章节。
- 理解知识需要跨越多个模块、文件或持久化边界，且具有独立、持久的范围时，可在已建立的 `docs/` 新建文档。例如安装归属与恢复、项目技能协调、CLI 自动化契约。
- 局部重命名、机械重构、单个函数即可说明的事实或测试夹具，不单独建文档。语义未变时仅修复受影响的路径、链接和锚点。
- 普通文档描述当前状态。需要长期保留背景、取舍和后果的重要决策放入 `docs/decisions/`，不从现有代码反向编造历史理由。
- 临时实施计划和验证进度不纳入正式文档。建库期间的唯一专用进度文件是 `docs/.project_doc_bootstrap.md`。

没有 `docs/` 时，常规任务先维护上述现有载体。用户要求建立、恢复或重整工程文档库时才进入 [建库流程](bootstrap_workflow.md)，不因发现一个新概念就附带创建整套目录。

## docs 目录与命名

文档根使用本技能约定的 `docs/`；用户或项目指令明确指定其他位置时调整技能入口与引用。以下规则只约束 Project Doc 库成员，不约束 README、技能包或源码目录。

- Markdown 文件名为 `[a-z][a-z0-9_]*.md`，目录名为 `[a-z][a-z0-9_]*`；各级入口固定为 `index.md`。
- 根目录路由根级文档和实际存在的分类；分类目录列出其拥有的每篇文档。
- 每篇正文恰有一个规范目录条目：根级正文归根目录，其余归所在分类。相关文档可以互链，不复制规范所有权。
- 分类按需求选用 `architecture/`、`domains/`、`interfaces/`、`operations/`、`decisions/`，不创建空分类或额外的通用 `project/` 层。
- 目录条目写清范围与读取时机，包含可用于定位的模块、命令或概念。

条目格式：

```markdown
- [项目技能协调](project_skills.md)：声明、受管目标和执行结果的关系。读取时机：修改 project apply/clean、agent 选择、接管或预演时。
```

示例路径仅在对应文档存在后使用。建库计划可写成 ``[planned] `project_skills.md`：范围与读取时机``，避免为尚未创建的正文生成失效链接。`planned`、`in_progress`、`verified`、`blocked` 仅用于建库期间；完成后移除临时状态。

## 正文结构

每篇正文具有一个 H1、简短范围说明、按语义组织的章节和必要的相关链接。需要频繁局部读取时加入章节导航；只有被代码引用的章节必须具有显式稳定 ID。

在关键契约附近给出仓库路径及相关符号或测试，方便重新核实，不把行号当作稳定身份。正文中的普通 Markdown 链接相对当前文档解析；代码锚点按 [锚点协议](anchor_protocol.md) 从仓库根解析。

写清能够影响实现或排障的约束，避免抄录完整源码、测试清单或 README。特别注意：

- 安装记录的归属、来源、目标和 scope 分别是什么。
- 操作是否只读、哪些步骤会写入，失败后哪些结果已经提交。
- CLI JSON、安装台账、操作日志 Journal 的 schema，以及 `arc.toml` 版本各自的兼容边界；核对各自的写入与读取校验入口。
- 用户可观察的例外和恢复条件；不要把“退出 0”“ok 为真”“没有待处理动作”当成同义词。

这些是核实维度，不要求每篇文档机械添加同样的章节。

## 同步、移动与删除

代码行为改变时，在同一任务中更新受影响正文、README 镜像、目录、链接和锚点。不要把文档同步扩展为无关重构或全库重写。

移动、合并或删除正文前，搜索目录条目、普通链接、源码锚点以及技能参考中的旧路径。保留仍有效的知识，逐个确定其新归属，再一起修复引用。主题仍受支持或仍有消费者时，保留现状和迁移说明；临时关闭不构成删除依据。

语义不变的章节保留稳定 ID。合并文档时把旧锚点映射到具体的新章节，不降级为整篇文档链接。已接受 ADR 的背景保持历史含义；后续决策替代它时，新建 ADR，旧记录标为 `superseded` 并互链，当前说明引用有效决策。

## 完成检查

1. 对照实现、调用方和测试核实变更涉及的契约，交叉检查 README 的中英文对应章节与实际存在的相关资源说明。
2. 检查目录条目、普通链接、代码路径和锚点目标存在；库成员有唯一规范条目，显式 ID 无重复。仓库导航中的路径写全到仓库根，逐项验证，避免靠“继承上一个目录”解析简写。
3. 移动或删除后搜索旧路径和旧 ID，处理仍表示有效引用的残留；历史说明中的文本按其含义判断。
4. 用 `git diff --check` 和内容差异检查本次修改。未跟踪或被忽略的文件需要另行比较实际内容，不能用空 Git diff 宣称没有变更；本技能也应检查当前跟踪状态。`.claude/skills` 与 `.codex/skills` 指向同一批文件时按实际路径去重，不复制第二份技能或替换链接。
5. 纯文档或技能变更完成上述结构与事实检查即可；Rust 变更还需运行相关测试及仓库要求的检查，具体入口见仓库导航。

使用 `rg`、文件读取和已有工具完成检查。需要搜索被忽略路径时显式传入该目录；不要默认遍历 `target/` 等产物。除非用户要求，不添加项目专用脚本、CI 或持久化的文档影响报告。
